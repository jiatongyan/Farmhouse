## 1. 产品概述

### 1.1 背景与问题

城市周边游、乡村体验游需求持续增长，农家乐成为热门出行选择。但传统农家乐服务信息分散，用户通常通过电话、微信或线下方式咨询和预订，存在以下问题：

- 农家乐服务信息不透明，价格、库存、可预订时间不清晰。
- 预订流程繁琐，用户无法在线完成下单与支付。
- 农户缺少统一的店铺和服务管理工具，库存与订单管理效率低。
- 热门农家乐服务在高峰期容易超卖，影响用户体验和商户信誉。

### 1.2 产品定位

农家乐出行选购平台是一个连接消费者与农户的在线服务预订平台。消费者可以在平台浏览、选购农户发布的农家乐服务，完成下单、支付；商户可以在平台管理店铺状态、发布和维护农家乐服务。

### 1.3 产品目标

- 为消费者提供便捷的农家乐服务浏览、下单、支付体验。
- 为农户提供店铺状态管理和服务管理能力。
- 建立可靠的库存扣减机制，避免超卖。
- 建设高可用微服务架构，保障系统在热门服务和多服务调用场景下的稳定性。
- 通过限流、熔断、降级等手段提升系统整体抗压能力。

### 1.4 用户角色

| 角色 | 说明 | 核心诉求 |
|------|------|----------|
| 消费者 | C端注册用户 | 浏览农家乐服务、查看详情、下单支付、查看订单 |
| 商户/农户 | B端入驻用户 | 管理店铺营业状态、发布/编辑/上下架服务、维护库存 |
| 平台管理员 | 平台运营人员 | 商户审核、服务审核、运营管理，本期可部分弱化 |
| 系统 | 网关、服务模块、中间件 | 提供路由、鉴权、库存、支付、消息、事务等能力 |

## 3. 核心业务流程

### 3.1 消费者下单支付流程

1. 消费者登录平台。
2. 浏览农家乐服务列表，进入服务详情。
3. 查看服务价格、可预订库存、商户店铺状态。
4. 选择数量，点击“立即预订”。
5. 系统校验库存，预扣库存，创建待支付订单。
6. 消费者选择支付方式并完成支付。
7. 支付成功回调，订单状态更新为已支付，库存确认扣减。
8. 若超时未支付，系统自动取消订单并释放库存。

### 3.2 商户发布服务流程

1. 商户登录商户端。
2. 设置店铺状态为营业中或休息中。
3. 新增农家乐服务，填写服务名称、描述、价格、库存数量、图片等信息。
4. 提交服务，服务状态为草稿或待上架。
5. 商户上架服务，消费者端可见。
6. 商户可随时编辑服务信息、修改库存、下架服务。

### 3.3 订单状态流转

```
待支付 -> 已支付 -> 已完成
   |          |
   v          v
已取消      已退款
```

- 待支付：订单创建成功，等待用户支付。
- 已支付：支付成功，库存确认扣减。
- 已完成：订单完成。
- 已取消：用户主动取消或超时未支付取消。
- 已退款：用户申请退款或平台取消后退款完成。

### 3.4 库存扣减与释放流程

```
下单 -> 预扣库存（可用库存减少，锁定库存增加）
        |
        +-- 支付成功 --> 确认扣减（锁定库存减少）
        |
        +-- 支付超时/订单取消 --> 释放库存（可用库存恢复，锁定库存减少）
```

库存模块必须保证任意时刻：

- 可用库存 >= 0
- 锁定库存 + 已售库存 <= 总库存
- 不出现超卖

## 5. 技术架构

### 5.1 总体架构

平台采用 SpringCloud 微服务架构，服务注册与配置中心使用 Nacos，网关统一入口，服务间通过 OpenFeign/RestTemplate 通信，使用 Sentinel 进行流量防护，使用 Seata 保证分布式事务，使用 Redis 缓存和分布式锁，RabbitMQ 处理异步消息。

```
客户端（消费者端 / 商户端）
        |
        v
   网关服务 Gateway
        |
        +------> 用户服务 User Service
        +------> 产品服务 Product Service
        +------> 订单服务 Order Service
        +------> 支付服务 Payment Service
        +------> 库存服务 Stock Service
        |
     Nacos（注册/配置中心）
     Sentinel（限流/熔断/降级）
     Seata（分布式事务）
     Redis（缓存/分布式锁）
     RabbitMQ（异步消息）
     MySQL（数据存储）
```

### 5.4 核心时序：下单扣库存

1. 消费者点击下单，请求经过网关鉴权后到达订单服务。
2. 订单服务调用库存服务进行库存预扣。
3. 库存服务使用 Redis 分布式锁锁定库存记录。
4. 库存服务通过 Lua 脚本原子校验可用库存，若充足则预扣：`available - quantity`，`locked + quantity`。
5. 预扣成功后返回结果，订单服务创建订单，状态为待支付。
6. 订单服务发送延迟消息，用于超时取消。
7. 用户支付完成后，支付服务回调订单服务。
8. 订单服务更新订单为已支付，库存服务确认扣减：`locked - quantity`。
9. 若订单超时未支付，订单服务取消订单，库存服务释放库存：`available + quantity`，`locked - quantity`。

### 5.5 高可用与服务保护

#### 5.5.1 多实例部署

所有核心微服务均采用多实例部署，注册到 Nacos。网关通过负载均衡策略分发请求。当某个实例宕机时，流量自动切换到其他健康实例，避免单点故障导致整个服务不可用。

#### 5.5.2 热点服务限流

针对访问量较大的热门服务接口，例如服务详情、库存查询、下单接口，使用 Sentinel 配置 QPS 阈值。当请求超过阈值时，返回友好提示，避免服务器过载。

#### 5.5.3 线程隔离与熔断降级

多个服务间存在调用链，例如下单调用库存、支付调用订单。为避免被调用服务异常导致调用方线程资源耗尽，系统通过 Sentinel 限制并发线程数。同时配置熔断规则，当异常比例或响应时间超过阈值时，自动熔断。下游服务异常时执行降级逻辑，返回兜底数据或友好提示。

### 5.6 线程安全与并发控制

#### 5.6.1 Redis 分布式锁防止库存超卖

下单时多个请求可能同时扣减同一库存，单纯依赖数据库更新可能导致超卖。项目使用 Redis 分布式锁保证同一库存记录串行扣减。锁的 Key 设计为库存记录粒度，例如：

```
lock:stock:{productId}:{stockDate}
```

通过 `SET key value NX EX` 获取锁，配合 Lua 脚本保证查询与扣减的原子性。扣减完成后释放锁。

#### 5.6.2 热门服务锁粒度优化

早期方案按商品或服务整体加锁，导致同一热门服务的所有下单请求串行，抢购耗时长。优化后，将锁粒度细化到具体库存记录，例如按服务 + 日期或按服务 + 场次维度加锁。这样可以并行处理不同库存记录的下单请求，减少锁竞争，缩短用户抢购耗时，提升系统吞吐。

## 8. 非功能需求

### 8.1 性能

- 热门服务详情接口 P95 响应时间 ≤ 200ms。
- 下单接口 P95 响应时间 ≤ 800ms。
- 系统在 500 并发下单场景下不超卖。
- Redis 热点库存读取性能满足 2000 QPS 以上。

### 8.2 可用性

- 核心服务整体可用性 ≥ 99.9%。
- 单实例宕机不影响整体服务。
- 限流、熔断、降级生效时返回友好提示，不影响系统稳定性。

### 8.3 安全

- 用户密码 BCrypt 加密存储。
- 接口使用 JWT 鉴权，网关统一校验。
- 支付回调校验签名，防止伪造。
- 接口防刷与限流，防止恶意请求。

### 8.4 扩展性

- 微服务可水平扩展，新增实例自动注册到 Nacos。
- 业务模块解耦，可独立迭代部署。
- 消息队列解耦订单超时、库存释放等异步任务。

### 8.5 可观测性

- 记录网关访问日志与关键业务日志。
- Sentinel 提供实时监控和规则管理。
- 后续可接入 Prometheus + Grafana 展示服务指标。

## 10. 风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|----------|
| 高并发下库存热点竞争激烈 | 下单耗时增加 | 细化锁粒度、Lua 原子扣减、Redis 集群 |
| 分布式事务一致性问题 | 订单、库存、支付数据不一致 | Seata 全局事务 + MQ 最终一致性补偿 |
| 服务间调用链路异常 | 雪崩、资源耗尽 | Sentinel 线程隔离、熔断、降级 |
| Redis 分布式锁失效 | 超卖风险 | 锁超时、Lua 原子操作、定期巡检 |
| 农家乐服务非标准化 | 库存模型复杂 | 支持按日期/场次维度管理库存 |

## 11. 验收标准

- 消费者可完成注册、登录、浏览服务、下单、支付全流程。
- 商户可完成店铺状态管理、服务发布、编辑、上下架。
- 高并发下单场景下库存准确，不出现超卖。
- 手动下线某服务实例后，系统仍可正常提供服务。
- 触发限流或熔断规则后，接口返回友好提示，不影响其他服务。
- 订单超时未支付自动取消并释放库存。
- 核心接口响应时间满足性能要求。

## 12. 项目亮点总结

1. **服务保护体系完善**：多实例部署、限流、线程隔离、熔断降级组合使用，显著提升系统稳定性和抗压能力。
2. **线程安全与并发优化**：基于 Redis 分布式锁和 Lua 脚本保证库存扣减原子性，并通过细粒度锁优化热门服务抢购性能。
3. **微服务架构落地**：网关、用户、产品、订单、支付、库存六大模块清晰拆分，结合 Nacos、Sentinel、Seata、RabbitMQ 形成完整微服务治理方案。
4. **分布式事务与异步解耦**：Seata 保证交易主链路一致性，RabbitMQ 处理订单超时、库存释放等异步任务。
